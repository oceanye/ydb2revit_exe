## 一、网格 152/154 等混凝土梁在 Revit 里缺失——根因与方案 A

### 1.1 排查链（数据三环全部完好，缺的是一个标高行）

```
① ydb 源数据：网格 152/154（2F 层）的混凝土梁是"降标高梁"
   2F：底 −3500 + 层高 5400 = 楼层顶 1900；梁带 HDiff = −1500
   → 梁顶实际标高 Z = 1900 − 1500 = 400（层间梁）
② 转换器：如实输出 → tbl1 中 329 根梁 Z=400（数据没丢）
③ 插件合并表：CombineBeam 覆盖 107 根（合并后）
④ tbl3 标高集合 = 楼层底 ∪ 楼层顶 = {−7200, −3500, 1900, 5100, …, 33900}
   → 【没有 400】（400 不是任何楼层的底或顶）
⑤ 插件建模：先按 tbl3 逐行创建 Revit 标高(Level)，再按每根梁的 Z 找
   同标高 Level（FindLevelAtElevation，1mm 容差）挂接
   → Z=400 找不到标高 → 这批梁创建失败被跳过 → 模型里"缺失"
```

### 1.2 影响面（全模型精确审计）

| 构件 | 缺失标高类别 | 数量 |
|---|---|---|
| 梁（tbl1） | **仅 Z=400 一类** | 329 根（合并后 107 根，含网格 152/154 的 400×800 混凝土梁） |
| 柱（tbl2） | 无 | 0 |
| 墙（tbl4） | 无 | 0 |

其余 16 个标高全部有对应 Level，无其他批量缺失。

### 1.3 方案 A 详解（在转换器内修复，插件零改动）

**原理**：把 tbl3 的集合定义从

```
标高集合 = ∪各层 LevelB（楼层底） ∪ ∪各层 (LevelB+Height)（楼层顶）
```

扩展为

```
标高集合 = 楼层底 ∪ 楼层顶 ∪ 构件实际标高补集
构件实际标高补集 = { tbl1/tbl2/tbl4 所有端点 Z 值 } − { 楼层底 ∪ 楼层顶 }
```

**实现要点**：

1. 转换器在装配完 tbl1/tbl2/tbl4 之后、写 tbl3 之前，收集全部构件端点 Z 值；
2. 沿用现有去重规则（按标高值，容差 1e-6）；
3. 新增标高行**续用 RFn 命名序列**（如 RF2=16795 已占用，则 400 命名 RF3），
   绝不与已有名重复（C# 端 Level.Name 重名会抛异常）；
4. 表结构不变（tbl3 仍为 Floor TEXT / LevelB REAL），纯加行，契约向后兼容；
5. 连续单栋/无降标高梁的模型：补集为空 → 输出与现状**逐行一致**（零回归）。

**插件端为什么零改动**：插件的模型是"tbl3 每行 → 创建一个真实 Level → 构件按 Z
找 Level 挂接"。加了行之后，插件会在 400 处自动多建一条真实标高（如 RF3），
降标高梁自然挂上——不改变插件任何代码与行为。

### 1.4 "构件标高补集"与 Revit"标高偏移"的区别（常见疑问）

| | 方案 A：补集 → tbl3 加行 | 标高偏移方式（未采用） |
|---|---|---|
| 原理 | 数据库 tbl3 多一行 → 插件创建**真实标高线**（如 400 处的 RF3） | 梁挂 1900 层，另设实例参数"起点/终点标高偏移 = −1500" |
| 改动方 | 仅转换器一个函数 | 必须改插件（读 HDiff、计算偏移、写参数） |
| Revit 里的表现 | 立面/标高明细表多一条 RF3 标高（外观代价小） | 无新增标高，但插件复杂度上升 |
| 与现架构契合度 | 完全契合（插件本来就是按标高找层） | 需要插件新增一条参数化路径 |

**结论：不是用标高偏移实现**，而是让插件按既有逻辑多建一条真实标高。

### 1.5 验收标准（执行后）

1. 颛桥重转后 `SELECT * FROM tbl3` 出现 Z=400 行（续 RFn 名）；
2. Revit 重导后：网格 152/154 的 400×800 混凝土梁出现，且梁顶标高 = 400；
3. 既有 17 个标高行不变（零回归）+ 全部回归测试通过；
4. exe 重打包并部署两个部署位。

## 二、PEC 截面"主表子表不一致"（1117 问题）详解与修复

### 2.1 YJK 的存储结构（Kind=209 PEC 截面写在两处）

| 位置 | 形态 | 内容 |
|---|---|---|
| **主表** `tblBeamSect` | 数值列 u/t/d/f | u=腹板厚、t=总高 H、d=翼缘宽 B、f=翼缘厚 |
| **子表** `tblSubSectionSect`（同 ID） | 形态一：SubKind=13 数值列 | 规范正常形态，应与主表一致 |
| 同上 | 形态二：Kind26 打包串（ShapeVal） | 标准热轧型钢目录定义：选择器 39 + 名称（如 HW200X200）+ Q16 定点 H/B |

### 2.2 矛盾现象（SectID=1117 三方对照）

| 数据源 | 内容 | 指向 |
|---|---|---|
| 主表数值列 | t=350, d=150, u=6, f=11 | H350x150x6x11（**陈旧值**） |
| 子表打包串 | 选择器 39 + 名称 HW200X200 + Q16 H=200/B=200（交叉一致） | **HW200X200** |
| YJK 界面 | 显示"类型1 HW200X200" | **HW200X200**（界面读的是子表目录名） |

成因推断：建模人把截面从自定义 H350x150x6x11 改为热轧 HW200X200 时，
YJK 更新了子表打包定义，但**没有刷新主表数值列**（导出数据缺陷）。
规范文档 §4.1 写"以主表数值为准"，其前提是"主表子表一致"（§4.2 要求
一致性校验）——1117 违反了该前提，规范规则在这类脏数据上与事实相反。

### 2.3 旧逻辑为什么错

旧转换器只要主表 t/d/u/f 有值就**根本不看子表** → 输出 H350X150X6X11@PEC
→ 颛桥 **3694 根梁**（1117 被 3392 段引用）带着错误截面进入 Revit
（用户抽查发现 6 处：359580/359712/…）。

### 2.4 修复方案（提交 399a825，已闭环验证）

**核心：优先级规则修订 + 完整校验链 + 回退点名**

1. **子表优先**：Kind=209 时，先尝试解码子表 Kind26 打包定义（长/短格式），
   **校验链全部通过才采用**：

   ```
   [0]=26 → 打包头解出选择器必须=39 → 名称（HW/HM/HN…）
        → Q16 的 H/B（[10]/[9]÷65536）与名称交叉一致（±0.5mm）
        → 长格式另有：[14]自定义标志=0（标准热轧）+ [41]尾部ID=截面ID
        → 厚度来源：四段式名称（H400X200X8X13）直接取名；
                     两段式名称（HW200X200）查内置 GB/T 11263-2017 国标表
                     （HW200X200 → 腹板 8 / 翼缘 12）
   ```

2. **短格式支持**（插件端 handoff 要求）：除 42 字段长格式外，支持 11 字段
   短格式——[1..3] 打包 12 字节（选择器+名称），[9]/[10] Q16；短格式无
   自定义标志/尾部 ID 列，这两项校验自动跳过。
3. **回退必须点名**：子表不可解码时才回退主表数值；若该截面**连可用子表
   都没有**（无行或数值全空），逐个记入转换结果 `warnings`（SectID+构件数），
   绝不静默。
4. **零回归**：长格式闭环截面（HN600X200 等 6 个）输出逐串不变；
   正常 SubKind=13 数值子表（主/子一致，双源互证）不受影响、不产生警告。

### 2.5 验证结果（三层闭环）

| 层 | 结果 |
|---|---|
| 数据 | H350X150X6X11 残留 **0**；H200X200X8X12@PEC **3744 根**；垃圾截面串 0 |
| 模型 | 重导成功（CombineBeam 4902 根、柱/墙回写齐备） |
| 人工 | 用户确认点名的 6 根梁 Revit 类型名 = H200X200X8X12，与 YJK 一致 |

# Handoff：颛桥 PEC 梁（Kind 209）截面无尺寸数据排查

排查日期：2026-09-02
输入：`颛桥测试版\dtlmodel.ydb`（插件端报"ShapeVal增强失败：ID33507 / 无法获取截面信息，
创建梁模型中止"的同一文件）

## 1. 现象与根因

转换器把无法解析四尺寸的 Kind-209 截面输出成 `209,33506@PEC`（原始 ShapeVal 直接拼
@PEC 后缀），C# 端按 PEC 截面解析失败 → 建模中止、异常弹窗循环。

根因：**该 ydb 中 6 个 PEC 梁截面的尺寸数据不存在任何文本字段中**。

## 2. 已核实事实（颛桥 dtlmodel.ydb 实测）

12 个 Kind-209 梁截面中 6 个正常（`tblBeamSect` 直接列 u/t/d/f 有值），6 个全零：

| SectID | 受影响构件数（按自然层实例） | ShapeVal 打包串中可辨认的 (b, h) |
|---|---|---|
| 33502 | 30 根 | (200, 600) |
| 33504 | 117 根 | (200, 500) |
| 33506 | 731 根 | (200, 400) |
| 33507 | 105 根 | (150, 400) |
| 33509 | 95 根 | (150, 300) |
| 33510 | 50 根 | (200, 200) |

已排除的存放位置：

* `tblBeamSect` 直接列（b/h/u/t/d/f）——全零；
* `tblSubSectionSect`（ID 与 SectID 相等，SubKind=26）——数值列同样全零，
  真实数据只在 `ShapeVal` 打包串里（见 §3）；
* `idNew` 指向的行——tblBeamSect 中不存在；
* `tblIShapeJGSect` / `tblBeamJGSect`——两表均为 0 行。

## 3. SubKind=26 打包串部分破译（假说，供确认）

`ShapeVal = "26, v1, v2, v3, 0×5, v9, v10, 0×4, v15, 0×n, ID,"`，每个 v 为 32 位整数
（两个 16 位值打包：`hi=v>>16`，`lo=v&0xFFFF`）。实测规律：

* **v9、v10 的 hi16 恰为 (b, h)**：如 13107200=0x00C80000→200；26214400=0x01900000→400
  ——6 个截面全部符合常规 GKL 规格（见上表），可信度高但未经 YJK 官方确认；
* v15 = (5, 0)；v1 只有两个取值；v2 低位为顺序号——含义未知；
* **腹板厚 tw、翼缘厚 tf 在本文件中未找到任何存放位置**（既不在打包串可辨认位置，
  也不在任何截面表）。

对照证据：SectID=1117 直接列有值（H350x150x6x11）但其 SubKind-26 打包串为 (200,200)，
与直接列不一致——说明打包串与直接列语义可能不同步，破译需谨慎。

## 4. 已实施的防护（ydb转换.py，caf299b 之后提交）

按"显式拒绝、不静默猜测"原则：转换前收集无法解析四尺寸的 PEC 截面，
**在写库前抛出机器可读错误**，点名全部 SectID 与受影响构件数，提示在 YJK 中补全
（或重选标准截面）后重新导出。颛桥实测输出：

```text
PEC 截面缺少尺寸数据，无法生成 H 截面字符串：梁截面 SectID=33502（30 根构件）；
梁截面 SectID=33504（117 根构件）；梁截面 SectID=33506（731 根构件）；
梁截面 SectID=33507（105 根构件）；梁截面 SectID=33509（95 根构件）；
梁截面 SectID=33510（50 根构件）。请在 YJK 中为这些截面补全尺寸（或重选标准截面）后重新导出 ydb。
```

配套回归测试：`test_dimensionless_pec_section_fails_explicitly`（34 项全过）。
exe 已重打包并部署两个部署位。
